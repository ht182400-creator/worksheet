## 4. 并发用例实现说明（TC-27 / TC-31 / TC-32）

SQLite + `TestClient` 存在两点工程限制，导致**真·线程并发**在单进程测试中不稳定：

1. `TestClient` 的 anyio portal 绑定主线程，跨线程调用会抛 "Task scheduler cannot be called from a thread that does not have an event loop"；
2. （**已修复**）`store.apply_status_change` 原为非原子**进程内版本校验**（`if orm.version != version`），单进程多线程下两个事务都会读到旧版本并都提交，乐观锁不真正生效。现已升级为 SQL 层 `UPDATE ... WHERE version=?`（影响行数 0 即视为冲突），`submit_report` 的工序合并也改为 `UPDATE ... WHERE version=?` 原子累加，真并发下乐观锁与在线合并均真正生效。

因此并发类用例采用**串行重放 / 多次累加**方式，稳定覆盖核心分支（满足验收口径）：

- **TC-27 乐观锁冲突**：新工单 `2→3`（200，version→2），再用旧 `version=1` 重放 `2→4`（state=3 的合法转移，避开 STATE_ILLEGAL 抢先拦截）→ 触发 `BIZ_VERSION_CONFLICT` 409。验证“旧版本必被拒”。
- **TC-31 在线合并无丢失**：同工序串行 5 次报工各 10 → `merged_completed` 累计 50。验证 BR-22 服务端自动合并（相对客户端二选一，杜绝丢失）。
- **TC-32 状态竞态**：`2→3` 成功后，重放 `2→1` 因 state 已变（`3→1` 不在 `STATE_TRANSITIONS[3]`）→ `STATE_ILLEGAL` 409。验证“状态已变致目标不在 allowedTransitions”。

> **状态（2026-07-23 全部落地）**：① SQL 层原子乐观锁、② 工序合并原子累加 已纳入 `test_smoke_db.py` 并 **CI 阻断**；③ **真实并发验证**已落地为独立测试 `test_concurrency.py`：临时库启用 WAL + `busy_timeout`，多线程直打 `store` 层（避开 TestClient/anyio 的文件锁抖动，同时仍是真并发）。
> - **TC-27（状态乐观锁）**：5 真实线程同提 `version=1` → 恰好 1 个成功（`version→2`），其余 4 个 409 `BIZ_VERSION_CONFLICT`。
> - **TC-31（报工在线合并）**：预建工序（merged=10）后 5 真实线程同提 `version=1` → 恰好 1 个报工成功（merged=20），其余 4 个 409 `BIZ_VERSION_CONFLICT`，**无静默丢更新**（失败方被拒而非覆盖，客户端重试）。
> - **TC-32（状态竞态）**：冲突源于**状态转移守卫**（`STATE_ILLEGAL`）而非版本锁，串行重放即充分覆盖，未纳入真并发（见 `test_cases.json` 该条 `real_concurrency=false` 备注）。

完整用例清单与字段（actual/result/automated/test_step）见 `backend/tests/test_cases.json`。
