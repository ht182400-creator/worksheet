# 工单智能识别与扫码分发系统 — PRD 场景化评审报告

**版本**：V1.0
**日期**：2026-07-23
**评审角色**：资深 B 端产品经理 + 用户研究员
**评审对象**：`工单智能识别与扫码分发系统-需求与架构文档_V4.1.md`（PRD 部分）
**评审方法**：场景化走查（用户旅程 / 状态机校验 / 边缘场景），聚焦"逻辑不通"与"反人类设计"

## 1. 🟠 D1：OCR 高错误率时人工修正成本反超手动录入

- **描述**：当整单 OCR 错误率 >50%（置信度普遍 <70%），文员需逐字段核校工单号、料号、PO、产量、交付日期等十余项。OCR 纠错库（§4.2）仅覆盖 `l→1 / O→0` 等简单字符易位，**不覆盖字段级语义错误**，逐字段修正的点击次数可能 > 直接重录，但文档未提供"跳过修正、直接空白重录"的快捷通道。
- **根本原因**：§3.3 / BR-02 只定义置信度**分级**（≥95% 自动 / 70–95% 审核 / <70% 重录），**未定义整单级阈值**；"重录"相对"修正"无快捷入口（如一键清空预填、表单预聚焦）。
- **人性化建议**：
  1. 增加**整单级阈值**（如关键字段错 ≥3 个或整单置信度 <60%）→ 直接给"新建空白工单"快捷通道，跳过 OCR 预填。
  2. 修正界面支持**字段级"采用原文 / 采用OCR / 清空"三态一键切换**，而非逐字编辑。
  3. 埋点 `correction_seconds`（§14.6 OCR span 已记 confidence，应补充），用数据反推是否真大于手录，驱动模板泛化（§24.2：>10 种格式属算法工作量）。

## 2. 🔴 D2：工人报工填错数量后无"撤回/更正"机制

- **描述**：工人把 100 填成 120（多填），因 120 ≤ 要求量，BR-05 防超报不拦截，系统直接接受，下游工序累计失真；少填则下游误判未完工。M5-03 报工"提交即入库"，幂等仅防重复提交、不防填错。文档无"报工撤销""更正单""班组长二次审核"任何设计。
- **根本原因**：§4.4 BR-05 只防**超报**，完全未定义"少报/多报后的更正/撤回"；状态机无"待确认"子态。
- **人性化建议**：
  1. 增加**报工撤回窗口**（提交后 N 分钟内本人可撤回，或状态未进下工序前可撤回）。
  2. 引入**班组长审核节点**（关键工序报工需主管确认，对应状态机加 `待确认` 子态）。
  3. 数量异常（同比历史偏差 >X%）触发**二次确认弹窗**（"您填写 120，历史均值 100，确认？"），用防呆代替事后纠错。

---

## 3. 🔴 D3：状态机只定义"有哪些状态"，未定义合法"跳转边"

- **描述**：§4.3 仅列 7 个状态码（0–6）与一句话说明，**无 allowedTransitions 显式定义**（§24.5 建议4 只提"后端返回 allowedTransitions"，PRD 正文从未画出转移矩阵）。技术上 `PATCH /status` 若只校验乐观锁不校验目标态合法性，**"已完成(5)"可被直接打回"待分发(2)"甚至"待识别(0)"**；"已关闭(6)"能否因冲突被重新打开亦未定义。BR-04 只要求记录"从什么变为什么"，**不禁止非法跳转**，等于事后审计而非事前拦截。
- **根本原因**：状态定义与状态流转规则分离，PRD 缺权威转移表。
- **人性化建议**：在 PRD 画**显式状态转移表**（如 `4生产中 → 只允许 → 5已完成 / 6已关闭`；`5已完成 → 只允许 → 6已关闭`，禁止回退；`6已关闭` 为终态不可变），作为 `state-machine` 接口权威数据源。明确"关闭后纠错"走**新建红冲工单**而非回退原单，避免历史数据被篡改。

## 4. 🔴 D4：同一工单两工人同时 Pad 报工，并发冲突处理对工人不友好

- **描述**：工人 A、B 同时打开工序页（均拿 version=10），A 先提交（version→11），B 再提交 version 不匹配 → 服务端返回 CONFLICT。此时 B 端弹"冲突解决 UI 让用户选保留方"（M5-11）——**但 B 是普通工人，不知 A 报了多少、该保留哪份**，把版本冲突裁决这一管理动作甩给一线工人是反人性的；BR-06 的 `conflict_logs` 最终"由用户选择保留方"未区分工人/主管权限。
- **根本原因**：在线并发与离线冲突共用一套"用户选保留方"逻辑，未区分角色与场景。
- **人性化建议**：
  1. **在线并发**不走"用户选保留方"，由**服务端按业务规则自动合并**（同工序累加已完成数量，取 `max(client_created_at)`），仅当累加超要求量才升级主管。
  2. "用户选保留方"冲突 UI **只限离线冲突且限主管/文员角色**（BR-10 已有角色，应在此强制）。
  3. 工人端冲突只显示"您的报工已记录，与同事数据合并中"，不暴露版本号概念。

## 5. 🔴 D5：大屏断网显示"僵尸数据"误导主管

- **描述**：BR-07 说大屏"SSE 推送、断线自动重连并全量同步"，BR-08 有超期红色闪烁，但**未定义断网期间视觉状态**。网络分区时 SSE 心跳失败但页面未崩，大屏静止显示最后一次快照，主管误以为"实时"；文档没要求显示"最后更新时间"和"数据可能延迟"角标。§5 验收只测正常态"刷新延迟 <5秒"，**未测断网态降级展示**。
- **根本原因**：异常/降级态的"用户可见性"设计空白。
- **人性化建议**：
  1. 大屏**常驻显示"数据更新于 HH:MM:SS"**，超过阈值（如 >30s 无推送）整屏变灰 + "连接中断，数据非实时"醒目横幅。
  2. 断网超 N 分钟自动切"上次同步时间 + 静态快照"模式并明确标注。
  3. 把"断网降级展示"补进 §21 异常场景与 §5 验收标准。

## 6. 🟠 D6：状态"已分发(3)"依赖二维码打印，但打印失败无回退

- **描述**：状态链 `2待分发 → 3已分发（二维码已生成待打印）→ 4生产中`。M3-02 批量生成"支持失败重试"，但**单张打印失败/贴错**时工人扫码无对应工单 → 无法报工，工单卡在"已分发"。文档未定义"打印失败/扫码无果"如何回退重打，也未给工人扫码空结果时的求助入口。
- **根本原因**：状态边界强依赖物理打印成功，缺失败回退与扫码兜底。
- **人性化建议**：
  1. 状态 3 细分为 `3a 已生成` / `3b 已打印确认`。
  2. 工人扫码"无工单"给**一键申请重打**入口（走主管审批）。
  3. 后台/大屏增加"已分发但未首扫超过 X 小时"预警，主动发现贴漏。

---

## 7. 🟠 D7：离线冲突解决 UI 要求工人"理解差异并二选一"，认知负荷过高

- **描述**：Story 五（§3.1）描述工人"回到有网后系统提示冲突，让我选择保留哪份"。但**工人不掌握管理视角全局数据**，强迫二选一极易选错；`conflict_logs` 仅"供管理员审计"——把责任推给工人、审计又滞后。
- **根本原因**：默认裁决策略错配角色，工人无能力做全局判断。
- **人性化建议**：默认策略改**"本地优先 + 标记待主管复核"**而非当场裁决；弹窗只说"您的数据已保存，但与主管修改有出入，已提交主管确认"，避免工人做他无能力做的判断；主管端（M6-12 冲突记录管理）才是裁决主场景，应强化而非把 UI 塞进工人 App。
